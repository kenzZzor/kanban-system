# Краткий контекст для AI-агента

Перед каждой задачей прочитай `AGENTS.md`, `docs/DEVELOPMENT_PLAN.md`, `docs/PROJECT_STATUS.md` и только те технические файлы, которые указаны в задаче или необходимы для понимания напрямую связанного кода.

## Источники истины

- `AGENTS.md` — постоянные правила работы с кодом, безопасность, тестирование и границы изменений.
- `docs/DEVELOPMENT_PLAN.md` — единственный источник истины для порядка реализации и целевых бизнес-требований. Не выбирай следующие этапы самостоятельно.
- `docs/PROJECT_STATUS.md` — фактически реализованное и незавершённое состояние. Обновляй только после проверки кода и тестов.
- `docs/API.md` — известные реализованные API-контракты; при сомнении проверяй реальный `route.ts` и сервис.
- `docs/DATABASE.md` — обзор существующей модели; `prisma/schema.prisma` остаётся техническим источником истины.
- `docs/ARCHITECTURE.md` — границы и зависимости модулей.

Другой документ с параллельной очередью этапов не используется: `docs/PRIORITIES.md` удалён в пользу единого плана. Если документы или код расходятся, сообщи о расхождении и не выдумывай контракт.

## Состояние реализации

Завершены session-based authentication, RBAC, Departments API, `GET /api/users` и Department Members API с операциями списка, добавления/реактивации, изменения роли/руководителя и мягкого удаления. Подробности и последние подтверждённые проверки — в `docs/PROJECT_STATUS.md`.

Ближайшая задача после отдельного подтверждения владельца — login UI и app shell; далее — UI подразделений и участников. API проектов, задач, рабочего времени, уведомлений и аналитики ещё не образуют завершённые пользовательские модули. Не подменять отсутствующий backend mock-данными.

## Обязательные ограничения

1. До изменения кода составь план: что проверить, какие файлы прочитать/изменить, какие проверки запустить. Жди явного одобрения владельца.
2. Реализуй только явно порученный срез. Не переходи к следующему этапу из плана без указания владельца.
3. Не меняй Prisma schema, миграции, зависимости или архитектуру без согласованной задачи и обоснования.
4. Сначала изучай существующую структуру и переиспользуй имеющиеся модули; не создавай параллельные каталоги и дубликаты.
5. Проверки доступа выполняются на сервере. Не доверяй непроверенным ID/ролям от клиента. Используй существующие Zod и permission mechanisms.
6. Для новых API используй проектный `apiHandler`/`requireUser`/AppError-механизм там, где он подходит. Не выдумывай новый формат ответа.
7. Мутация и требуемая Activity/Audit должны быть атомарными, если это предусмотрено бизнес-правилом. Переиспользуй имеющиеся transaction helpers и сервисы.
8. Не делай посторонний рефакторинг, обновление версий, новые функции или фиктивные API «заодно».
9. Не выполняй `git commit`, `git push`, `git reset`, `prisma migrate reset` и разрушительные команды БД. Коммит делает владелец после ревью.
10. В финале перечисли изменённые файлы, миграции/env, результаты проверок и требуемые ручные проверки.

## Финальная UX-полировка ошибок

Общая доработка понятного пользовательского отображения ошибок выполняется последним этапом `docs/DEVELOPMENT_PLAN.md`. В ранних срезах при этом обязательны базовая обработка ошибок API, корректная валидация и отображение ошибок без сокрытия причин.
