# Kanban System — единый план разработки

> **Назначение документа:** это единый источник истины для последовательности разработки, требований к будущим функциям и согласованных бизнес-правил. Пользователь и AI-агент должны следовать этому плану при подготовке и выполнении задач.
>
> **Текущая реализация описывается отдельно:** см. [`PROJECT_STATUS.md`](PROJECT_STATUS.md). Наличие требования в этом документе означает, что функция запланирована или описана как целевая, а не то, что она уже реализована.

## 1. Как пользоваться планом

1. Перед каждой задачей сверить этот документ с [`PROJECT_STATUS.md`](PROJECT_STATUS.md), [`AGENTS.md`](../AGENTS.md) и нужными техническими справочниками.
2. Выбирать только следующий согласованный с владельцем проекта срез. Наличие более позднего этапа в плане не разрешает агенту начинать его самостоятельно.
3. До изменения кода агент изучает перечисленные в задаче файлы, предлагает план изменений и ожидает подтверждения владельца.
4. Реализация выполняется вертикальными срезами: модель данных при необходимости → серверная логика и сервис → разрешения → валидация → API → UI → Activity/Audit и уведомления, если требуются → тесты.
5. После среза проверяются относящиеся к нему тесты, typecheck и lint; при необходимости сборка и E2E. Владелец проверяет diff и делает Git-коммит.
6. После подтверждения завершения обновляется `PROJECT_STATUS.md`. Требования и порядок в этом документе изменяются только по согласованному решению, а не автоматически по предположению агента.

`AGENTS.md` определяет постоянные технические ограничения; данный документ — продуктовые требования и порядок этапов; `PROJECT_STATUS.md` — фактическое состояние. `API.md`, `DATABASE.md` и `ARCHITECTURE.md` служат справочниками и не переопределяют план.

## 2. Продукт и обязательные принципы

Kanban System — внутренняя корпоративная система для организации подразделений, управления задачами, междепартаментного взаимодействия, контроля выполнения, аналитики и учёта рабочего времени.

- Архитектура: модульный монолит Next.js App Router, TypeScript strict, PostgreSQL и Prisma.
- Сервер является источником истины для аутентификации, доступа, бизнес-правил, статусов, длительности и аудита.
- UI работает только с реально существующими API. Запрещено маскировать отсутствующий backend фиктивными пользователями, задачами, графиками или аналитикой.
- Существующая Prisma-модель не является подтверждением готовой функции: для завершения нужны серверная логика, разрешения, валидация, UI требуемого сценария и проверки.
- Критические изменения и соответствующая Activity/Audit-запись должны быть атомарными, если для события предусмотрено журналирование.
- Любой экран должен поддерживать loading, empty/no-results, error и permission states. Доступность не должна зависеть только от цвета или мыши.
- Полировка единого пользовательского отображения ошибок откладывается до последнего этапа. Это не отменяет корректной серверной валидации, HTTP-статусов и обработки ошибок в каждом раннем срезе.

## 3. Роли и границы доступа

Точная проверка доступа всегда выполняется на сервере. Клиентское скрытие кнопок не заменяет разрешения API.

| Роль | Область и целевое поведение |
|---|---|
| `SYSTEM_ADMIN` | Глобальная системная роль, не привязанная к одному подразделению. Административные операции в рамках системных permissions; может назначать `DEPARTMENT_ADMIN`. |
| `DEPARTMENT_ADMIN` | Роль в конкретном подразделении. Управляет составом и ролями участников в пределах своих полномочий; не может удалять последнего активного администратора подразделения. Нельзя удалить участника с активными подчинёнными, пока не исправлена иерархия. |
| `MANAGER` | Роль в конкретном подразделении. Управляет рабочими задачами в рамках своих полномочий и может назначить задачу самому себе. Отдельно учитываются ограничения на пользователей, подразделения и задачи. |
| `EMPLOYEE` | Выполняет доступные ему задачи; не получает полномочий управлять участниками или ролями только потому, что видит задачу. |
| `VIEWER` | Режим чтения. Получает сводный аналитический экран и доступ к аналитическим показателям, разрешённым для его scope; не может выполнять управляющие мутации. |

`SYSTEM_ADMIN` глобален; остальные перечисленные роли задаются через `DepartmentMember`. Для каждой операции с задачей дополнительно проверяются источник, назначенное подразделение, исполнитель, состояние задачи и право пользователя на конкретное действие.

Аналитический доступ `VIEWER`, `MANAGER` и `DEPARTMENT_ADMIN` должен соответствовать их разрешённому набору данных. По умолчанию department-scoped роль не означает глобальный доступ ко всем подразделениям. Если требуется общеорганизационный обзор для `VIEWER`, это нужно утвердить отдельно.

## 4. Требования к задачам и Kanban workflow

### 4.1 Основные участники задачи

В доменной логике следует различать:

- создателя задачи;
- человека, который назначил задачу исполнителю (инициатора назначения);
- текущего исполнителя;
- исходное подразделение;
- подразделение, которому поручено выполнение;
- проект, если задача к нему относится;
- историю назначений и переходов.

Не предполагать, что создатель задачи, инициатор назначения и исполнитель — всегда разные или всегда одинаковые пользователи. Текущую схему и историю изменений нужно проверить до выбора миграции.

### 4.2 Пять стадий Kanban и возврат постановщику

Целевое требование владельца проекта — пять основных этапов и возможность для постановщика увидеть, кем, как и когда выполнена работа. Рабочий вариант для согласования:

1. **Новая задача**.
2. **На анализе**.
3. **В работе**.
4. **На проверке у постановщика** — исполнитель завершил свою часть и передал результат на проверку.
5. **Завершена** — постановщик подтвердил итог.

Это предлагаемая интерпретация, а не уже утверждённый API-контракт. До реализации Task API и финальной модели статусов нужно подтвердить, что возврат постановщику должен быть отдельной четвёртой стадией перед окончательным завершением. Альтернативный вариант — завершать задачу сразу и показывать её в истории/списке постановщика — нельзя подменять первым вариантом без согласования.

До утверждения workflow не считать старые коды статусов в Prisma окончательным набором пользовательских колонок. Нужно сопоставить текущие `TaskStatus`/seed и целевой пятиэтапный процесс миграцией или иным явным механизмом, не оставляя противоречивые статусы в UI.

При подтверждении стадии проверки должны быть определены:

- кто может отправить задачу на проверку;
- кто является постановщиком, имеющим право подтвердить или вернуть задачу;
- может ли постановщик быть не создателем задачи;
- что происходит при смене исполнителя или повторном назначении;
- как вернуть задачу на доработку с комментарием и полной историей;
- кто и когда может повторно открыть завершённую задачу.

События назначения, переходов, отправки на проверку, подтверждения и возврата должны попадать в Activity/Audit, где это предусмотрено моделью событий.

### 4.3 Учёт времени задачи

При назначении задачи должен начинаться серверный учёт времени. Требуется показывать:

- общее время выполнения задачи;
- время, проведённое на каждой стадии;
- даты/время назначения, каждого перехода, отправки на проверку и окончательного завершения;
- историю повторных переходов и возвратов на доработку.

Источником истины являются серверные timestamps и история событий/статусов. Таймер в браузере может обновлять отображение, но не должен быть источником сохранённых длительностей.

Общее время не сбрасывается при смене исполнителя или возвращении задачи на доработку. Повторные пребывания в одной стадии должны суммироваться корректно. Длительность статуса и общее elapsed time не равны фактически отработанным сотрудником часам. Базовый вариант для обсуждения — считать длительность задачи и стадий по календарному времени; если нужно дополнительно считать только рабочие часы, этот показатель должен опираться на утверждённый календарь и модель посещаемости.

Перед проектированием БД зафиксировать, считается ли интервал до окончательного подтверждения постановщиком частью общего времени выполнения и как отображаются паузы, блокировки и закрытые/отменённые задачи.

### 4.4 Назначение задачи самому себе

`MANAGER` должен иметь возможность назначить задачу самому себе. Серверная политика назначения не должна отклонять такой сценарий только из-за совпадения инициатора назначения и исполнителя. При этом сохраняются обычные проверки scope, членства, статуса задачи и журнала действий.

### 4.5 Одна и та же работа нескольким сотрудникам

Менеджер должен иметь возможность выбрать нескольких сотрудников и поручить им одну и ту же работу одной операцией.

**Рекомендуемая модель по умолчанию:** создавать связанные индивидуальные задачи — по одной на каждого выбранного исполнителя — с общим исходным шаблоном/группой массового назначения. Каждая задача имеет независимые статус, исполнителя, таймер, историю, комментарии и результат. Завершение одним сотрудником не завершает работу за остальных. UI может показывать общий прогресс группы и прогресс каждого участника.

Это нужно отличать от одной общей задачи с несколькими соисполнителями, у которой общий статус. Для второго подхода отдельно пришлось бы определить владельца завершения и распределение времени между сотрудниками. Не реализовывать обе модели одновременно без отдельного решения. До миграции проверить, какая связующая сущность нужна для массовой операции и отображения её результатов.

### 4.6 Позиция и конкурентные изменения

Текущая схема, согласно последней проверенной документации, не содержит `Task.position` и `Task.version`. Перед Kanban drag-and-drop их наличие нужно проверить в `prisma/schema.prisma`. Целевой дизайн должен предотвращать потерю обновлений при одновременном изменении одной задачи и обеспечивать стабильный порядок карточек. Поля и миграции утверждать только после изучения текущей схемы.

### 4.7 Междепартаментная работа

Нужно поддержать различимые сценарии:

1. **Прямое назначение** задачи другому подразделению — если права и политика разрешают.
2. **Запрос другой команде** — исходное подразделение создаёт запрос, целевое подразделение принимает/отклоняет его и назначает исполнителя.

Должны сохраняться исходное подразделение, целевое подразделение, исполнители и история передачи. Исполнитель должен принадлежать активному членству в `assignedDepartment`. Все действия проверяются на сервере и фиксируются в истории. Запрос/принятие — отдельный процесс со статусами; его нельзя имитировать одним лишь изменением `assignedDepartmentId`.

## 5. Учёт рабочего времени сотрудников

### 5.1 График и расчёт нормы

Базовый график: **09:00–18:00**, включая **1 час обеденного перерыва**. Это 9 часов между началом и окончанием дня и 8 часов целевого учитываемого рабочего времени без обеда.

Пример: отметка входа в 11:00 и выхода в 18:00 дают 7 часов между отметками. При вычете 1 часа обеда учитывается 6 часов работы; относительно 8-часовой нормы недоработка составляет 2 часа.

В плане зафиксирована договорённость об одном часе обеда. До реализации нужно определить, вычитается ли полный час автоматически для каждого дня или перерыв отмечается фактически, а также как оформляется отсутствие/перенос обеда. Не менять пример расчёта без отдельного решения.

### 5.2 Вход, выход и запись рабочего дня

Требование — ежедневная авторизация сотрудника и явная отметка начала и окончания рабочего дня. Учёт рабочего времени должен храниться отдельно от web session: срок cookie, закрытие вкладки, истечение сессии или технический logout сами по себе не дают достоверной информации о фактически завершённой смене.

Целевой сценарий:

- при первой успешной авторизации в рабочий день система фиксирует начало рабочего дня либо запрашивает подтверждение начала, если есть неоднозначность;
- повторный login в тот же день не создаёт дублирующий рабочий день;
- для завершения работы сотрудник выполняет явную отметку выхода/завершения рабочего дня;
- интерфейс не позволяет незаметно считать день закрытым, если отметка отсутствует;
- техническое завершение web session и бизнес-событие завершения рабочего дня проектируются как разные понятия, даже если в UI они будут связаны одним действием.

До реализации требуется согласовать поведение кнопки «Выйти»: завершает ли она одновременно рабочий день или должна предлагать отдельное подтверждение. Не закрывать смену автоматически только из-за истечения cookie.

### 5.3 Недоработка и контроль руководителя

Система сравнивает учитываемое время с нормой 8 часов и рассчитывает дефицит. Если норма не выполнена, результат должен быть доступен менеджеру соответствующего подразделения для контроля дисциплины. Уведомление/событие должно сохранять дату, расчёт, основание и статус обработки.

Нужны состояния для пропущенного входа, незакрытого дня, повторной отметки, отсутствия, ручной корректировки и подтверждения руководителем. Не интерпретировать незакрытую смену автоматически как ноль часов без процедуры уточнения.

До миграции определить правила для выходных и праздников, отпусков/больничных и иных отсутствий, удалённой работы, сверхурочной работы, гибкого графика, корректировки отметок руководителем, повторного открытия исправленной записи и временной зоны организации. График 09:00–18:00 является исходным требованием, но нельзя жёстко зашивать временную зону и календарные исключения в UI.

### 5.4 Разграничение с таймером задачи

Посещаемость сотрудника и длительность задачи — разные модели и разные метрики. Сотрудник может быть на работе 8 часов, но задачи могут ожидать анализа или проверки. Нельзя автоматически считать все 8 часов рабочей смены временем одной назначенной задачи. Связь этих показателей в аналитике должна быть явной.

## 6. Аналитика и роль VIEWER

Планируется единый обзорный экран для `VIEWER`, показывающий основные показатели в одном месте. Аналитика также доступна `MANAGER` и `DEPARTMENT_ADMIN` в рамках их полномочий.

Целевые наборы показателей, подлежащие уточнению по мере появления реальных данных:

- количество задач и распределение по стадиям;
- новые, завершённые, просроченные и возвращённые на доработку задачи;
- длительность выполнения и времени на каждом этапе;
- нагрузка и ход выполнения работ по сотрудникам;
- запросы и передачи между подразделениями;
- соблюдение рабочего графика, недоработки и незакрытые рабочие дни — с ограничением по доступу к персональным данным.

Не создавать dashboard с фиктивными цифрами до готовности API. Расчёты и фильтры должны выполняться на основе реальных данных и серверных правил scope. По умолчанию аналитика `VIEWER` ограничена разрешёнными ему подразделениями; глобальный обзор следует выдавать только по утверждённым полномочиям.

## 7. Activity, Audit и уведомления

Activity — читаемая история действий; Audit — журнал важных изменений, требующий надёжного сохранения. Там, где событие обязательно, бизнес-мутация и запись истории должны быть атомарными.

Целевые события включают создание/назначение задачи, смену исполнителя, переход статуса, отправку постановщику, подтверждение или возврат, массовое назначение, междепартаментную передачу, комментарий, отметки рабочего дня, выявленную недоработку и изменение записи посещаемости.

Уведомления добавляются только для определённых продуктовых событий. Как минимум, нужно спроектировать уведомления о новом назначении, задаче на проверке у постановщика, возврате на доработку, междепартаментном запросе и выявленной недоработке, направляемой менеджеру. Не обещать уведомление в UI, пока серверная генерация и доставка не реализованы.

## 8. Порядок реализации

Следующий список — **порядок разработки**, а не отчёт о текущем состоянии. Фактическое состояние хранится отдельно в `PROJECT_STATUS.md`.

### Этап 1. Frontend foundation: вход и оболочка приложения

- Реализовать UI входа по существующему `POST /api/auth/login`.
- Восстанавливать пользователя через `GET /api/auth/me` и текущую cookie/session-модель.
- Реализовать защищённую точку входа в приложение и переиспользуемую оболочку с sidebar, содержимым и данными текущего пользователя.
- Реализовать выход через существующий `POST /api/auth/logout`.
- Состояния loading, invalid credentials, unauthenticated и API error; не начинать общий рефакторинг UX ошибок.
- Junie сначала предоставляет план и ждёт подтверждения. Backend authentication/RBAC/schema не менять.

**Критерии завершения:** реальные auth endpoints, корректные редиректы, отсутствие mock users, доступность клавиатурой, релевантные тесты, typecheck, lint и сборка.

### Этап 2. UI подразделений и участников

- Список подразделений через существующий `GET /api/departments`.
- Список участников и формы добавления/реактивации, изменения роли и руководителя, мягкого удаления через существующие endpoints.
- Отражать запреты и результаты сервера; не считать client-side скрытие контролов механизмом безопасности.
- Обработать пустой список, отсутствие доступа, конфликт, валидацию и подтверждение разрушительных действий.

**Критерии завершения:** UI работает с реальным API, не содержит фиктивных записей, соответствует серверным permissions и покрыт целевыми проверками.

### Этап 3. Проекты: проектирование и backend API

### Этап 6. Модель данных и миграции задач

- Спроектировать историю переходов и назначений, необходимую для расчёта длительности этапов и общего времени.
- Спроектировать связанное групповое назначение и индивидуальные задачи, если подтверждена рекомендуемая модель.
- Не запускать destructive migrations или reset без явного разрешения. Проверить миграции и обратимость/безопасность переноса данных.

- Поддержка менеджером назначения задачи самому себе.

### Этап 8. Workflow, постановщик и учёт времени задач

- Реализовать этап проверки постановщиком, подтверждение завершения и возврат на доработку — после утверждения логики.
- Фиксировать серверное время назначения и каждого изменения статуса.
- Рассчитывать общее elapsed time и длительность каждой стадии с учётом повторных заходов.
- Не смешивать длительность стадии с учётом рабочего времени сотрудника.

## 9. Решения, которые необходимо явно подтвердить до соответствующих этапов

Следующие вопросы нельзя молча решать на усмотрение Junie:

1. **Постановщик и пятиэтапный workflow:** четвёртая стадия — «На проверке у постановщика», пятая — «Завершена», или задача сразу завершается и показывается назначившему? Кто именно подтверждает: создатель, инициатор последнего назначения или отдельный requester?
2. **Таймер задачи:** базовые длительности по календарному времени или только по рабочему календарю? Рекомендуемый стартовый вариант — серверное elapsed time и длительность каждой стадии; расчёт рабочего времени отдельно опирается на Attendance.
3. **Массовое назначение:** подтверждаем рекомендуемую модель связанных индивидуальных задач вместо одной общей задачи с несколькими исполнителями.
4. **Обед:** автоматически вычитать один час либо учитывать фактические отметки начала/конца перерыва; как фиксировать исключения.
5. **Вход/выход:** считается ли нажатие «Выйти» завершением рабочего дня одновременно с logout; что делать при истёкшей сессии или закрытом браузере без checkout.
6. **Расписание:** календарь выходных, праздничных дней, отпусков, отсутствий, гибкого графика и сверхурочных.
7. **VIEWER:** общая аналитика означает весь доступный ему набор показателей в пределах своего подразделения или глобальные показатели компании? Ролевые права должны быть согласованы до выдачи междепартаментных данных.
8. **Повторное открытие задачи:** кто может вернуть уже подтверждённую задачу в работу и как при этом пересчитываются итоговые сроки/длительности.

До закрытия каждого соответствующего решения можно реализовывать независимые предварительные этапы, но нельзя строить на предположении финальную модель данных или workflow, которую будет дорого менять.

## 10. Критерии завершения любого среза

Срез считается законченным, когда выполнены применимые требования:

- проверены существующие файлы и реальные контракты;
- реализованы серверные business rules, permissions и валидация, когда они требуются;
- реализованы UI happy path и негативные состояния, если срез включает UI;
- критические мутации журналируются в соответствии с правилами Activity/Audit;
- нет фиктивных данных вместо отсутствующего backend;
- добавлены релевантные unit/API/Playwright/E2E-тесты;
- пройдены назначенные проверки typecheck, lint, тесты и при необходимости build;
- обновлены технические документы и `PROJECT_STATUS.md`;
- владелец рассмотрел diff и выполнил Git-коммит.
