# API Reference

Этот документ перечисляет только маршруты, которые уже реализованы в приложении. Наличие модели в Prisma не является подтверждением готового endpoint. Для точного Zod-контракта и новых полей при изменениях всегда сверяться с соответствующим `route.ts` и сервисом.

## Соглашения

- Базовый адрес локальной разработки: `http://localhost:3000`.
- Защищённые маршруты используют серверную сессию в cookie `kanban_session`.
- Авторизация проверяется на сервере. Скрытие элемента UI не заменяет проверку permission.
- Новые маршруты должны использовать проектный `apiHandler`, `requireUser`, существующие error-классы и Zod-проверки там, где это соответствует текущему API-слою.
- Формат ошибок в старых и новых маршрутах ещё не полностью унифицирован. Некоторые legacy-маршруты `/api/auth/login`, `/api/auth/me` и `/api/departments` используют собственные ответы; новые маршруты, обёрнутые `apiHandler`, используют общий формат проекта. Не делать предположений о едином payload ошибки для всех endpoints без сверки конкретного route handler.

## Реализованные маршруты

| Метод и путь | Доступ | Назначение / ответ |
|---|---|---|
| `POST /api/auth/login` | Без активной сессии | Принимает `email`, `password`; создаёт серверную сессию и устанавливает HttpOnly cookie. |
| `POST /api/auth/logout` | С cookie сессии; операция идемпотентна по смыслу | Удаляет текущую серверную сессию, очищает cookie. |
| `GET /api/auth/me` | Требуется активная сессия | Возвращает текущего пользователя или `401`. |
| `GET /api/users` | Permission `USERS_READ` | Возвращает список пользователей без `passwordHash`, включая системную роль. |
| `GET /api/departments` | Требуется активная сессия | Системный администратор с `DEPARTMENTS_READ` видит все подразделения; остальные получают список подразделений, связанных с их членством. |
| `POST /api/departments` | Permission `DEPARTMENTS_MANAGE` | Создаёт департамент. Вход: `name` (обязательное, до 200 символов), `description` (необязательное, до 1000 символов). Успех — `201` с `{ department }`. |
| `GET /api/departments/:departmentId/members` | Permission `MEMBERS_READ` в указанном департаменте | Возвращает `{ members }` только для активных членств (`leftAt: null`), с полями пользователя, роли и руководителя. |
| `POST /api/departments/:departmentId/members` | Permission `MEMBERS_MANAGE` в указанном департаменте | Добавляет или реактивирует членство. Вход: `userId`, `roleCode`, опционально `managerId`. Возвращает `{ member }` и `201`. |
| `PATCH /api/departments/:departmentId/members/:memberId` | Permission `MEMBERS_MANAGE` в указанном департаменте | Меняет `roleCode` и/или `managerId`. Для очистки руководителя `managerId` можно передать как `null`. Требуется хотя бы одно изменяемое поле. |
| `DELETE /api/departments/:departmentId/members/:memberId` | Permission `MEMBERS_MANAGE` в указанном департаменте | Мягко прекращает членство через `leftAt`; физически пользователя не удаляет. |

## Membership: валидация и ограничения

`roleCode` для членства принимает `DEPARTMENT_ADMIN`, `MANAGER`, `EMPLOYEE` или `VIEWER`. Системная роль `SYSTEM_ADMIN` не назначается как department membership role.

- Пользователь должен существовать и быть активным.
- Повторное добавление активного участника возвращает конфликт. Участника с завершённым членством можно реактивировать.
- Назначаемый руководитель должен быть активным участником того же департамента.
- Нельзя назначить `DEPARTMENT_ADMIN` без соответствующих системных полномочий.
- Проверяются иерархические циклы и недопустимый руководитель.
- Нельзя удалить последнего активного `DEPARTMENT_ADMIN`.
- Нельзя удалить участника, у которого остаются активные подчинённые, пока не исправлена иерархия.
- Изменения, требующие Activity, выполняются совместно с записью Activity; обработка некоторых конкурентных изменений использует сериализуемую транзакцию с повторными попытками.

## Ещё не реализовано

В текущем API нет полноценных endpoints для:

- CRUD проектов и участников проектов;
- создания, чтения, изменения и архивирования задач;
- переходов статусов, назначения исполнителей и изменения порядка задач;
- комментариев;
- междепартаментного назначения и request/accept flow;
- уведомлений и пользовательской ленты Activity;
- Kanban board и dashboard.

Пока эти маршруты не созданы и не протестированы, frontend не должен подменять их имитацией готового API.
