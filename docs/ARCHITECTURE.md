# Архитектура

## Архитектурный стиль

Kanban System использует **modular monolith**: одно Next.js-приложение, единая серверная кодовая база и PostgreSQL. Микросервисы не вводятся без отдельного архитектурного решения.

```text
Browser
  │
  ▼
Next.js App Router
  ├── Pages / UI (в разработке)
  ├── Route Handlers: app/api/**
  ├── Authentication: lib/auth/**
  ├── API error/handler utilities: lib/api/**
  ├── Authorization: lib/permissions/**
  ├── Business services: lib/services/**
  ├── Activity logging: lib/activity/**
  └── Prisma access: lib/db.ts + transaction helpers
             │
             ▼
          PostgreSQL
```

Схема показывает логические границы, а не требование создавать отдельную папку под каждый блок. Новые каталоги добавляются только по необходимости и в соответствии с существующей структурой.

## Основные границы

- `app/` — маршруты Next.js, страницы и API Route Handlers.
- `lib/auth/` — определение текущего пользователя, пароли и сессии.
- `lib/api/` — общие обработчики API и типы ошибок для маршрутов, использующих этот слой.
- `lib/permissions/` — коды прав, политика и проверка доступа.
- `lib/services/` — бизнес-операции, которые должны быть повторно используемыми вне Route Handler.
- `lib/activity/` — создание записей Activity.
- `lib/db.ts`, `lib/db-transaction.ts` — Prisma-доступ и транзакционные helper-функции.
- `prisma/` — схема, миграции и seed.
- `tests/` — unit- и Playwright/API-тесты.

Фактический состав и размещение файлов репозитория важнее примерной схемы. Не создавать параллельные каталоги (`lib/db/`, `lib/validation/` и т. п.) только ради соответствия абстрактному шаблону.

## Аутентификация и роли

Аутентификация основана на серверной сессии. Клиент использует защищённую cookie сессии, сервер извлекает текущего пользователя и проверяет активность учётной записи. UI-проверки не являются механизмом защиты.

Ролевая модель разделяет два scope:

- `SYSTEM_ADMIN` — системная роль пользователя, глобально не привязанная к одному подразделению.
- `DEPARTMENT_ADMIN`, `MANAGER`, `EMPLOYEE`, `VIEWER` — роли membership в конкретном департаменте, связь хранится в `DepartmentMember`.

Доступ проверяется на сервере по permission-кодам. Роль пользователя не следует определять по имени, выбранному департаменту в UI или клиентскому состоянию.

## Структура организации

`DepartmentMember` представляет членство конкретного пользователя в подразделении. Роль и руководитель хранятся на уровне этого членства. `managerId` указывает на другое членство, что позволяет представить иерархию внутри департамента. `leftAt` означает, что членство прекращено; строка сохраняется для истории и повторной активации.

Реализованные ограничения membership включают проверку менеджера в том же департаменте, защиту от циклов и самоназначения руководителя, запрет удаления последнего активного администратора и запрет удаления руководителя, пока у него есть активные подчинённые.

## Задачи и междепартаментная работа

Текущая схема данных уже предусматривает `Task`, исходный департамент (`sourceDepartmentId`), назначенный департамент (`assignedDepartmentId`), исполнителя, проект, статус, приоритет и тип задачи. Но полноценных Task API, серверной политики `can(user, action, task)`, переходов статусов и пользовательского workflow пока нет.

Целевой междепартаментный процесс должен отдельно учитывать исходный департамент, принимающий департамент, исполнителя и историю действий. Нельзя считать этот процесс реализованным только потому, что поля присутствуют в схеме.

## Транзакции и Activity

Критические бизнес-изменения, требующие Activity, должны выполняться вместе с записью истории в транзакции. Существующие операции Department Members используют сериализуемые транзакции с повторными попытками для выбранных конфликтов. Новые операции должны следовать установленному в репозитории подходу, а не реализовывать параллельный механизм.

## Принцип развития

Функции реализуются вертикальными срезами: данные → серверная логика/API → авторизация → UI → Activity/Audit и другие побочные действия → тесты. Конкретный порядок этапов и продуктовые требования задаются `docs/DEVELOPMENT_PLAN.md`; текущее состояние хранится отдельно в `docs/PROJECT_STATUS.md`, а постоянные правила разработки — в `AGENTS.md`.
